# INNERSPACE — Demonstration Evidence Plan

**Internal candidate register · No media approved or attached · Portfolio remains private**

This document defines the evidence that may be selected for an eventual public Innerspace showcase. It is **not** itself a claim that every screenshot, video, or real-world demonstration exists or has been independently verified. Only source-backed, personally reviewed, sanitized media should be added to a public presentation.

**Critical separation:** A rendered architecture diagram is explanatory material, not an actual photograph, screenshot, runtime benchmark, or hardware demonstration. Never label a simulated robot as a real working robot.

## Candidate gallery structure

A future public page could carry three approved items: (1) a high-level architecture diagram that names product roles but not private endpoints; (2) one sanitized, dated acceptance-result screenshot with a source/verification category; and (3) one authorized, edited demonstration clip showing the application consuming infrastructure, clearly labeled as *simulation*. More items should be added only as reviewed evidence becomes available.

For each real capture, retain a private record of:

| Required metadata | Meaning |
| --- | --- |
| Evidence ID / source | Internal provenance reference to the retained original. |
| Product and version/checkpoint | Exactly what was running; no accidental conflation with later milestones. |
| Observed behavior | What the capture actually depicts, without assumptions. |
| Verification boundary | Native test, simulation, two-client desktop/VR, physical hardware, or other explicitly confirmed category. |
| Public caption | Non-sensitive statement that a visitor can independently understand. |
| Disclosure review | Owner approval of specific redacted bytes and exact public version. |
| Integrity | Source hash and approved derived-public-file hash retained privately. |

## Mandatory disclosure screening

Before attaching a screenshot, animated diagram, video, document, log, or sound recording:

- Remove secrets, tokens, cookies, serial numbers, private contact information, and unintended identity data.
- Review source code, internal architecture, protocol endpoints, private paths, network addresses, service ports, repository content, and other proprietary implementation details visible on screen.
- Inspect visible windows, notifications, browser tabs, HUD overlays, terminal output, filenames, filenames embedded in video frames, metadata, and background audio.
- Check rights to any external assets, music, voice samples, maps, models, and third-party content.
- Ensure captions match the **exact demonstrated test** and its known limitations.
- Preserve originals and any detailed acceptance records privately; export a separate redacted derivative with a verified digest.
- Audit **all Git history** before making the portfolio public. Repository history is not hidden by deleting a file from the latest commit.

## Robotics evidence gate — not satisfied by simulated game tests

Any future claim of *physical-world working robots* needs evidence from actual hardware, measured payload/speed/force behavior, controlled work areas, sensing and emergency-stop tests, hazard/risk assessment, and operator-reviewed safety validation. Moving-company autonomy and safety are **not accepted achievements** in the current Build220/Build221 records. They belong to a future engineering qualification program.

## Commercial release hold

This document and the broader portfolio currently remain private. Uploading a sanitized demonstration here would still require explicit review before public visibility. The product repositories, SDK source, model assets, full receipts and binaries are not part of any public showcase.
